# 适配台账

每次微信升级、重新定位补丁点后，在这里追加一行。**这张表是下次适配的起点**：
同类漂移往往重复出现，先看历史怎么处理的，能省掉大半功夫。

字段说明：

| 字段 | 含义 |
|---|---|
| 日期 | 完成适配并验证的日期 |
| 微信版本 | 安装目录名，如 `4.1.15.53` |
| 原始 SHA256 | **未打补丁**的 `Weixin.dll` 哈希，用来确认"我分析的是哪份文件" |
| 补丁点 | 文件偏移（`0x` 十六进制）+ 对应 VA |
| 指令 | 改动前后的 7 字节 |
| 漂移 | 相对上一条特征码，哪些字节变了 |
| 验证 | 做到哪一步：`副本全流程` / `真机启动` / `撤回实测` |
| 记录人 | 谁做的，出问题找谁 |

- `4.1.12.0 ~ 4.1.15.x` 这一行只说明"特征码区间覆盖到这里"，不代表每个小版本都验证过。

  `wxar/patterns.json`。

## 怎么填一行

```powershell
# 1) 确认分析的是哪份文件（必须是未打补丁的原始 DLL）
Get-FileHash "C:\Program Files\Tencent\Weixin\<版本>\Weixin.dll" -Algorithm SHA256

# 2) 定位补丁点
python tools/relocate.py --dll "<原始 DLL 副本>"

# 3) 记录漂移：工具会打印「第 N 字节: 期望 XX 实际 YY」
#    没有输出就是无漂移

# 4) 验证，按做到的程度勾选
python -m wxar patch   --file "<副本>" --yes --no-elevate   # 副本全流程
python -m wxar restore --file "<副本>" --yes --no-elevate
python -m wxar patch                                        # 真机
#    然后自己发一条消息撤回，看原消息是否保留                    # 撤回实测
```

## 已知的漂移类型

适配时优先对照这几种，命中率高：

| 类型 | 表现 | 处理 |
|---|---|---|
| disp32 变化 | 落在 `?? ?? ?? ??` 里 | 本来就不参与匹配，忽略 |
| 立即数变化 | 锚点内非修改位字节变了 | 两侧同时放开成 `??`（`relocate` 自动做） |
| opcode 变化 | 第 1 字节 `89` 变了 | **拒绝自动生成**，人工确认新指令语义 |
| 函数被内联/拆分 | 字符串引用的位置变了 | 按 `docs/ADAPTING.md` 第 3 节手工定位 |
| 版本区间失效 | 报「没有适配 X 的特征码」 | 补 `min_version` / `max_version` 区间 |
